# Model card: `txcat-categorizer`

Bank-transaction categorizer served by the txcat API. This card describes the registered
champion, `txcat-categorizer` version 2 (`tfidf-logreg-lexicon`).

## Model

- **Task:** assign one of 19 spending categories (Income, Transfers, Groceries,
  Telecom & Airtime, …; see `txcat.data.taxonomy`) to a bank-statement description.
- **Input:** the description, cleaned by `txcat.data.clean` (NFKC, lower-case,
  references/dates/phone numbers removed, Ge'ez script kept), plus the sign of the amount
  (money in vs out; unknown when no amount is given).
- **Architecture:** word 1–2-gram and character `char_wb` 2–5-gram TF-IDF, a one-hot
  money-direction feature, and multinomial logistic regression (`class_weight="balanced"`,
  C chosen on validation).
- **Output:** a category and a confidence (the top class probability). Predictions below
  the **review threshold (0.418)** are flagged `needs_review` and stored in the review queue.
- **Format:** scikit-learn pipeline saved with skops, a format that only loads allow-listed
  types. Tracked in MLflow; the API serves an exported copy without MLflow.

## Training data

| Source | Rows | Licence / provenance | Role |
|---|---|---|---|
| Synthetic Ethiopian-style statements (`txcat.data.synthetic`) | 32,876 | Generated by this project (seeded). **Synthetic: not real customer data.** Every row has `source='synthetic'` | Train / validation / test |
| [`bukolafatunde/personal-finance`](https://www.kaggle.com/datasets/bukolafatunde/personal-finance) | 806 | Real-format US personal transactions, 2018–2019. **Licence unknown**, so it is used for research/demo only and never redistributed (the repo only holds the download script) | Train / validation / test |
| [`lowlevelexe/malaysian-semantic-transaction-dataset`](https://www.kaggle.com/datasets/lowlevelexe/malaysian-semantic-transaction-dataset) | 32,000 phrases | CDLA-Permissive. Merchant/keyword phrases, no dates or amounts | Extra training text only |

Raw data is never committed. It is downloaded or generated by `txcat data download` /
`txcat data build`. The synthetic generator draws merchants from a catalog of real
Ethiopian brands and institutions (CBE, telebirr, Ethio Telecom, …); the transactions,
people and amounts are invented.

## Evaluation

**Protocol.** Time-based split *per source*: oldest 70% train, next 15% validation,
newest 15% test (synthetic test: Feb–Jun 2025; Kaggle test: Jul–Sep 2019). Hyperparameters
and the threshold are chosen on validation and the test slice is scored once. Model
selection uses the mean of synthetic and Kaggle macro-F1. *Unseen text* = test rows whose
cleaned description never appears in the training transactions.

| Model (test slice) | Macro-F1 synthetic | Macro-F1 Kaggle | Macro-F1 unseen text (812 rows) |
|---|---|---|---|
| Rule baseline (merchant catalog + keywords) | 0.988 | 0.915 | 0.920 |
| TF-IDF + LogReg | 1.000 | 0.983 | 0.997 |
| **TF-IDF + LogReg + lexicon (this model)** | **1.000** | **0.991** | **0.996** |
| Multilingual MiniLM embeddings + LogReg | 0.994 | 0.992 | 0.957 |
| Multilingual MiniLM embeddings + LightGBM | 0.987 | 1.000 | 0.923 |

**Review threshold.** The lowest confidence at which auto-accepted *validation*
predictions are ≥97% accurate on each source separately. On the test slice it
auto-accepts 99.9% of rows, and those are 100% accurate. On the Kaggle test rows it
auto-accepts 98.4% at 100% accuracy.

Per-category F1, confusion matrices and split boundaries for every run are logged to
MLflow (`evaluation/` artifacts). The generated tables are in `reports/`.

## Intended use

- Demonstrating an end-to-end categorization system: pre-filling categories for personal
  finance views and budgeting, with a human review queue for uncertain cases.
- Statement descriptions in the style of Ethiopian banks and wallets (English, Amharic
  and mixed), and US card/bank exports similar to the Kaggle data.

**Out of scope:** credit, lending, fraud or any other decision about a person; production
use on real customer data without re-training and re-evaluating on that data; languages
or banking formats not represented above.

## Limitations

- **The headline numbers are optimistic.** Synthetic descriptions are template-generated
  from a fixed merchant catalog, so the synthetic test slice resembles training and scores
  ~1.0. They show that the pipeline works, not how it would do on real statements.
- **Little real data.** The real-format Kaggle test slice has 123 rows, and 121 of them
  repeat descriptions seen in training, so one error moves macro-F1 by several points.
- **Unseen merchants.** Character n-grams handle typos and new reference numbers well
  (0.996 on unseen text), but a merchant absent from training and from the lexicon is
  mostly guessed from generic words. Those predictions tend to have low confidence and go
  to review, which is the intended safety net, not a guarantee.
- **Category coverage.** Kaggle data covers 12 of the 19 categories. Savings, Community &
  Charity, Cash Withdrawal and some others are learned from synthetic data only.
- **Confidence is not calibrated** beyond the threshold choice. Treat it as a ranking, not
  a probability.
- **Amount use is minimal.** Only the sign of the amount is used, so the same description
  with very different amounts gets the same category.
- **Feedback loop.** Reviewed corrections are stored for retraining, but retraining on
  them isn't automated yet. Before using them, check for reviewer bias, such as people
  only correcting obvious errors.

## Ethical considerations

- The model sees transaction text, which can contain names and phone numbers. Cleaning
  strips reference and phone numbers, and the synthetic data uses invented names. A real
  deployment would need consent, access control and retention rules for both stored
  transactions and the review queue.
- Spending categories can reveal sensitive information (health, religion via church or
  mosque giving, debt). Insights built on them should be shown only to the account holder.
- The API has no authentication yet. An API-key header is planned before any public
  deployment.
